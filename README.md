# MATRYOSHKA Portable OS

**Независимый исследовательский виртуальный компьютер и гостевая ОС. Функциональная база: MATRYOSHKA Termux v0.3.2 / T1A.**

Portable OS развивается отдельно от основной **StyleOS**. Этот репозиторий содержит собственную виртуальную машину M32, гостевые прошивку, ядро, оболочку и приложения, экспериментальный процессор M8 и отдельную лабораторию движка. Код, архитектурные решения и дорожная карта StyleOS сюда не переносятся.

«Матрёшка: Разрыв ОС» — историческое рабочее название проекта. Текущий результат — работающий учебный прототип, а полноценная конкурентоспособная ОС остаётся долгосрочной целью. Поддержка GUI, `.tea`, APK и EXE ещё не реализована.

## Происхождение и границы переноса TASK-P0

Исходная точка — [LPYURA2/OS, коммит c5b62a4b4fc19d6db25d53f52eebcfba89dae708](https://github.com/LPYURA2/OS/commit/c5b62a4b4fc19d6db25d53f52eebcfba89dae708): **76 отслеживаемых файлов**, Git tree `54edc8639102e0ea63638fc5fc6ad7d6ded83351`. Коммит и его история перенесены в [LPYURA2/Portable-os](https://github.com/LPYURA2/Portable-os) без преобразования бинарных образов.

Первый снимок Portable-os побайтно соответствует указанному исходному коммиту. После него разрешённое документальное изменение ограничивается этим `README.md` и сохранением прежнего README в [docs/README_BASELINE_v0.3.2.md](docs/README_BASELINE_v0.3.2.md). Получается 77 отслеживаемых файлов. CPU, ISA, ABI, syscalls, ASM, тесты и системные образы сохраняют исходные байты; перенос не является новой функциональной версией ОС.

Операции TASK-P0 направлены только в Portable-os. Основной репозиторий `LPYURA2/OS` при переносе не редактируется, его история не переписывается. Удалённая вершина `main` источника проверена до переноса и после публикации исходного снимка: `c5b62a4b4fc19d6db25d53f52eebcfba89dae708` в обоих случаях. Операции записи в исходный OS не выполнялись; перед завершением TASK-P0 состояние источника проверяется ещё раз.

Чтобы посмотреть исходный состав и сохранённый README:

```sh
git ls-tree -r --name-only c5b62a4b4fc19d6db25d53f52eebcfba89dae708
git show c5b62a4b4fc19d6db25d53f52eebcfba89dae708:README.md
```

Не выполнять `git checkout` старого снимка поверх рабочей папки с личными данными. Исторические инструкции из документов относятся к своим этапам; актуальные команды для этого репозитория приведены ниже.

### Хост и гость

**Хост** — Python, запущенный в Termux или Linux. Он моделирует CPU, RAM, ROM, дисковый контроллер, ввод/вывод и аппаратные механизмы контекстов. Двухпроходный ассемблер и упаковщик образов также работают на хосте.

**Гость** — машинный код M32 из `firmware.asm`, `kernel.asm` и `programs/*.asm`. Решения загрузчика, планирование и обработка системных вызовов находятся в гостевом ASM. Python исполняет соответствующие инструкции и обеспечивает моделируемые устройства. Это позволяет изучать настоящую цепочку исполнения, сохраняя честную границу между аппаратной эмуляцией и логикой гостевой ОС.

### Память, ROM и диски

| Область | Назначение |
|---|---|
| `0x0000–0x1FFF` | ROM 8 КиБ; хост устанавливает `images/firmware.bin`, CPU начинает с адреса 0 |
| `0x2000` | Адрес загрузки и входа ядра; ядро читает с диска гостевая прошивка |
| `0x7000` | 512-байтный временный буфер заголовка/каталога |
| `0x8000 + ID × 0x3000` | Фиксированные слоты приложений по 12 КиБ; shell имеет ID 5, адрес `0x17000` |
| `images/system.img` | Системный образ 128×512 байт, 64 КиБ; для гостя только чтение |
| `matryoshka_user_disk.img` | Отдельный пользовательский writable образ 128×512 байт; появляется при запуске, исключён из Git |

`system.img` содержит заголовок `MTRX` в секторе 0, ядро в секторах 1..N (не более 16), каталог `MAPP` в секторе 17 и бинарники приложений начиная с сектора 18. Каталог v1 имеет 16-байтный заголовок и записи по 40 байт: имя, адрес загрузки, начальный сектор, число секторов, длина, сумма и флаги.

Пользовательское хранилище пока представляет одну `NOTE.TXT` в секторе 80: сигнатура `MNT1`, байт длины и до 90 байт UTF-8. Это демонстрация устойчивого хранения, полноценной файловой системы с каталогами ещё нет. Хост записывает образ через временный файл, `fsync` и `os.replace`; данный механизм не доказывает завершённую защиту от всех сбоев питания.

`images/shell.bin` сохранён для прежней диагностической сборки с адресом `0x8000`. При загрузке v0.3.2 используется `images/apps/shell.bin`, собранный для `0x17000` и упакованный в `system.img`. Два файла имеют разное назначение.

## Загрузка ОС и выполнение приложений

```text
Python: модель CPU/памяти/устройств и firmware.bin в ROM
    ↓ CPU начинает исполнять гостевую ROM
firmware → system.img: MTRX → ядро в RAM 0x2000
    ↓ проверка аддитивной суммы и JMP 0x2000
kernel → сектор 17: каталог MAPP
    ↓ выбор ID, проверка слота, чтение секторов 18..127
app binary → фиксированный слот RAM → checksum → SPAWN
    ↓ гостевой планировщик
shell / hello / counter / taskmgr / diskdemo / selfmod
```

1. `boot()` создаёт начальное состояние и переносит прошивку в ROM. Ядро и приложения не копируются в RAM из ASM хостом при запуске.
2. Firmware читает сектор 0 в `0x7000`, проверяет `MTRX`, положительную длину и число секторов 1..16. Через порты `OUT 50` (сектор), `OUT 51` (RAM), `OUT 52` (READ) и `IN 53` (статус) загружает ядро в `0x2000`.
3. Гостевой CPU суммирует 32-битные little-endian слова загруженных секторов. При успехе firmware передаёт управление ядру; неверный заголовок или сумма приводят к `BOOT ERROR` и остановке.
4. Ядро читает `MAPP`, проверяет каталог, получает ID стартовых программ из boot-profile портов и вызывает собственный `load_program`.
5. До дискового чтения проверяется гостевая таблица `slot → PID`. Для свободного слота проверяются адрес и размеры, читаются сектора бинарника, сверяется сумма, затем выполняется привилегированная `SPAWN`.
6. Shell `run N` использует `TRAP 10` для того же загрузчика. Исполнение процесса происходит в user mode; syscall или таймер возвращают управление гостевому ядру. Квант по умолчанию — 6 пользовательских инструкций.

Аддитивная сумма нужна для обнаружения части случайных повреждений. Она не является криптографической подписью или доказательством подлинности программы.

### Системные вызовы текущего ядра

Номера приведены для существующего экспериментального ABI M32. Это описание сохранённой реализации, а не новый интерфейс.

| `TRAP` | Действие |
|---|---|
| `1` | Вывести байт/символ из `R0` |
| `2` | Добровольно уступить выполнение планировщику |
| `3` | Завершить текущий процесс |
| `5` | Вывести буфер: `R0` — адрес, `R1` — длина |
| `6` | Передать сектор пользовательского диска: `R0` — сектор, `R1` — буфер, `R2` — 0 для чтения / 1 для записи |
| `7` | Узнать статус PID из `R0`, получить результат в `R0` |
| `8` | Прочитать байт клавиатуры, результат в `R0` |
| `9` | Очистить текстовый экран |
| `10` | Запустить ID приложения из `R0`; результат 0 при успехе, `0xFFFFFFFF` при отказе |

Причина 0 используется таймером; другие необработанные причины передают управление планировщику. Инструкции `SPAWN`, `SWITCH`, `STATUS`, `BLOCK`, `SETRET` и доступ к портам — привилегированные механизмы модели CPU, которыми пользуется гостевое ядро. Самовольное изменение ISA, ABI, номеров вызовов или форматов дисков не входит в перенос.

### Гостевые программы

| Команда shell | Программа | Действие |
|---|---|---|
| `run 0` | `hello` | Печатает сообщение из гостевого user mode |
| `run 1` | `counter` | Печатает числа 1..5; демонстрирует разделение CPU между задачами |
| `run 2` | `taskmgr` | Учебный вывод статусов процессов |
| `run 3` | `diskdemo` | Демонстрация блочного I/O; **записывает сектор 3 пользовательского диска** |
| `run 4` | `selfmod` | Учебная модификация собственных машинных инструкций |

Shell дополнительно поддерживает `help`, `ps`, `info`, `clear`, `save <text>`, `load`, `ls`, `rm`, `exit`. `save` меняет заметку, `rm` удаляет её. `ls` показывает учебную NOTE.TXT, а не каталог полноценной ФС.

## Запуск на Android / Termux

Для основной VM нужен **Python 3.9+ со стандартной библиотекой**. `pip`-зависимостей и root-доступа нет. Создайте новую рабочую папку; сохранённые диски прежних версий остаются в их каталогах.

```sh
pkg install python git coreutils -y
cd ~
git clone https://github.com/LPYURA2/Portable-os.git matryoshka-portable
cd matryoshka-portable
python --version
python matryoshka.py --selftest
python tools/export_images.py --check
python -m unittest discover -s tests -v
sha256sum -c CORE_SHA256SUMS.txt
python hardware_m8/m8.py --selftest
python hardware_m8/gate_alu.py
python matryoshka.py --os
```

Если папка `~/matryoshka-portable` уже существует, используйте новое имя и не распаковывайте файлы поверх пользовательского диска. Клонирование исходников из GitHub не требует доступа к общему Android-хранилищу.

После появления **`M:>`** команды вводятся уже в гостевой shell:

```text
help
run 0
run 1
```

Дождитесь завершения счётчика из-за известного CONSOLE-001, затем:

```text
ps
info
exit
```

Для учебного хранения в новом тестовом диске можно выполнить `save Привет, Матрёшка!`, `load`, `exit`, снова запустить `--os` и проверить `load`. Не переносите личный диск поверх другого файла. Перед любой ручной миграцией остановите обе VM и сделайте отдельную резервную копию.

Чтобы явно выбрать новый пользовательский образ:

```sh
python matryoshka.py --os --disk ./portable_practice_user_disk.img
```

`portable_practice_user_disk.img` — личные данные, исключённые правилом `*user_disk*.img` в исходном `.gitignore`. Стандартный путь `matryoshka_user_disk.img` также исключён из индекса. При выборе другого имени образа не добавляйте личный диск в Git.

Другие режимы VM:

```sh
python matryoshka.py --help
python matryoshka.py --run --apps hello,counter --disk ./practice_user_disk.img
python tools/show_components.py
```

`--run` выполняет выбранный гостевой профиль без интерактивной shell; `--os` запускает оболочку. Самотест M32 и unittest используют временные пользовательские образы и не требуют реального диска владельца. Самотест M8 имеет отдельный побочный эффект пересборки, описанный ниже.

## Сборка и проверка

### M32: бинарники и системный образ

Готовые воспроизводимые образы уже включены в Git. Для обычного запуска пересборка не нужна.

```sh
# Проверка соответствия текущих ASM, бинарников и manifest без записи:
python tools/export_images.py --check

# Явная пересборка после намеренного изменения ASM в отдельной копии:
python tools/export_images.py
python tools/export_images.py --check
```

Режим без `--check` изменяет `images/firmware.bin`, `kernel.bin`, оба набора shell/app бинарников, `system.img` и `manifest.json`. Пользовательский диск он не трогает. После изменения кода прежний `CORE_SHA256SUMS.txt` закономерно перестанет описывать новую сборку: не обновляйте его автоматически для сокрытия различий.

Сокращённый существующий скрипт `sh tools/check_baseline.sh` запускает только selftest M32 и проверку образов. Полная проверка приведена ниже.

### M8: самостоятельный аппаратный стенд

M8 имеет 25 опкодов, трёхбайтные инструкции, четыре тактовые фазы T0..T3, регистры A/B по 8 бит и PC/X по 16 бит, флаги Zero/Carry. Адресное пространство 64 КиБ разделено на ROM 32 КиБ и RAM 32 КиБ. ROM-монитор занимает 418 байт.

```sh
python hardware_m8/m8.py --selftest
python hardware_m8/gate_alu.py
```

Отдельная явная сборка/демонстрация, при необходимости в учебной копии:

```sh
python hardware_m8/m8.py --build
python hardware_m8/m8.py --run
```

Команды `--build` и `--run` пересобирают `boot.bin` и `boot.hex`; `--run` также запускает монитор. **`--selftest` M8 тоже записывает заново `hardware_m8/boot.bin` и `hardware_m8/boot.hex`.** В TASK-P0 этот тест выполнялся во временной копии проекта, а байты публикуемых артефактов сверялись с исходным коммитом. Они не переносят ядро M32 на M8 и не создают готовую Proteus-схему. Файлы `rom32k.bin/.hex`, `golden_trace.csv`, диаграмма и руководство сохранены как отдельные артефакты. `gate_alu.py` проверяет 327680 комбинаций пяти операций через модель логических вентилей, без электрических задержек и без запуска Proteus.

### Ограничения проверки

- `CORE_SHA256SUMS.txt` содержит 34 записи и не является хеш-манифестом всех 77 документов/артефактов. Полноту первоначального переноса подтверждают отдельное сравнение Git tree с исходным коммитом и сохранение бинарных байтов.
- Selftest и unittest не доказывают промышленную безопасность, устойчивость к любому power-cut или отсутствие всех гонок.
- M8/ALU tests являются программными эталонами. Физическая/Proteus-схема ими не подтверждена.

## Отдельная лаборатория движка `engine_lab`

Движок работает **на хосте Linux**, вне гостевой ОС. Он не добавляет GUI в M32 и не является runtime для гостевых C#, Python или Java. API использует программный framebuffer 480×270, рисование сцены, сохранение PPM и C ABI без SDL.

| Часть | Назначение | Статус проверки TASK-P0 |
|---|---|---|
| C, `src/mw_engine.c`, `include/mw_engine.h` | Память framebuffer, примитивы, экспорт C ABI | Собирается с C++ сценой |
| C++, `src/mw_scene.cpp`, `src/demo.cpp` | Сцена и нативный demo-клиент | **PASS**, кадр создан |
| Python, `python/demo.py` | Вызовы нативной библиотеки через `ctypes` | **PASS**, кадр совпадает с C++ побайтно; checksum `dc0b9529` |
| Java, `java/MatryoshkaEngine.java`, `src/mw_jni.c` | JNI-обвязка C ABI | **SKIPPED**: в окружении нет `javac` |
| C#, `csharp/MatryoshkaDemo.cs*` | Пример P/Invoke, проект .NET 8 | **SKIPPED**: в окружении нет `dotnet` |

В исторических документах есть прежний Linux-результат одинаковых кадров C++/Python/Java. Он не заменяет текущую проверку Java. C# остаётся исходным примером без подтверждённой сборки в доступном окружении.

Для Linux с установленными `gcc`/`g++` либо `clang`/`clang++`, Python 3 и, опционально, JDK:

```sh
cd engine_lab
bash build.sh
cd ..
```

Скрипт создаёт `engine_lab/build/libmatryoshka_engine.so`, C++ demo и кадры, запускает Python, а Java запускает только при наличии `javac` и `java`. Затем `tests/verify.py` сравнивает доступные кадры. Сообщение об успешном сравнении C++/Python при отсутствии JDK не означает, что Java была проверена.

Опциональная попытка сборки на Termux:

```sh
pkg install clang python -y
cd engine_lab
CC=clang CXX=clang++ bash build.sh
cd ..
```

Для Java дополнительно нужна доступная в репозиториях Termux JDK, например `openjdk-21`, и корректные JNI include paths. Код build.sh использует Linux JNI include directory, поэтому может потребоваться отдельная согласованная адаптация под Android. **Сборка движка в Termux в TASK-P0 не подтверждена.** .NET 8 SDK для C# также проверяется отдельно; наличие `.cs`/`.csproj` не означает рабочий порт .NET.

Альтернативная сборка C/C++ средствами CMake 3.16+:

```sh
cmake -S engine_lab -B engine_lab/build-cmake
cmake --build engine_lab/build-cmake
```

CMake собирает native library и C++ demo; Python/Java/C# этот проект автоматически не тестирует. Каталоги локальной сборки, кадры и кеши не входят в исходные 77 файлов. Не добавляйте их в импорт случайно.

## Ограничения и известные проблемы

- **CONSOLE-001:** фоновые процессы и shell пишут в общий терминальный канал. Счётчик может перемешивать вывод с набираемой командой и приглашением. Ожидание конца вывода — временный обход, исправление ещё не выполнено.
- **Не более 8 PID за один boot.** Идентификаторы не переиспользуются; завершившийся слот можно освободить для нового кода, но общий счётчик созданных процессов продолжает расти. Повторный запуск не бесконечен.
- **Фиксированные адреса приложений.** Бинарник связан для своего 12-КиБ слота; перенос в другой слот без пересборки/релокации неверен. Динамической линковки и стабильного продуктового ABI нет.
- **Повреждение образа останавливает загрузку.** Есть отказы на неверных заголовках/суммах, но автоматическое восстановление, резервный boot, A/B update и secure boot отсутствуют.
- **Учебная защита памяти.** Модель CPU проверяет границы и привилегированные инструкции; это не промышленная изоляция, не MMU уровня современной ОС и не песочница для недоверенного кода.
- **Хранилище ограничено NOTE.TXT.** Полноценной ФС, директорий, общей модели файлов и прав, журналирования и доказанной crash consistency нет.
- **GUI отсутствует.** Текстовый экран — устройство хоста. `engine_lab` не интегрирован в guest и не меняет этот статус.
- **`.tea`, APK, EXE отсутствуют.** `.tea` — целевое расширение, формат/ABI/пакетный менеджер только проектируются; совместимость конкретных категорий APK/EXE потребует отдельных runtime/API и тестовых матриц.
- **M32 и M8 несовместимы.** Они не запускают один kernel.bin. Единой утверждённой ISA для Termux ↔ Proteus нет; RV32I/RV32IM остаётся предложением ADR-001.
- **Портов PC/Limbo/ARM64 нет.** Схема Proteus не запускалась. Сетевой стек, современные драйверы, энергоменеджмент и производственная модель доступа ещё не реализованы.

## Учебный маршрут владельца

### Пять терминов на реальных файлах

- **Исходник:** `programs/hello.asm` — текст с командами и метками, который читает человек.
- **Машинный код:** `images/apps/hello.bin` — байты инструкций M32, которые декодирует `VirtualMachine.step()`.
- **Системный образ:** `images/system.img` — секторы с ядром, каталогом и бинарниками. Пользовательская NOTE.TXT находится в отдельном диске.
- **Git-коммит:** снимок отслеживаемых файлов с идентификатором SHA и ссылками на историю. `main` — ветка, указывающая на принятую вершину. Отдельный README-коммит меняет документацию и не создаёт новую версию CPU.
- **ISA и ABI:** ISA определяет команды процессора; ABI — договор бинарника с ядром/платформой, включая syscalls и адреса. Их изменение сделало бы перенос функциональной разработкой и могло бы сломать существующие образы.

### Практика без изменения базы

1. Откройте `programs/hello.asm` и найдите `.ascii` со строкой приветствия.
2. В `kernel.asm` найдите `load_program`, `OUT 50`, `OUT 51`, `OUT 52`, `IN 53` и `SPAWN`. Проследите, как адрес RAM и номер сектора доходят до эмулируемого устройства.
3. В `matryoshka.py` найдите `assemble()`, `VirtualMachine.step()` и `_guard()`. Сравните сборку программы, исполнение инструкции и проверку доступа.
4. Запустите `python tools/show_components.py` и сопоставьте карту с найденными участками.

Когда понадобится попробовать изменение текста `hello`, создайте отдельную учебную копию/ветку и отдельный пользовательский диск. В ней измените только строку `.ascii`, соберите `python tools/export_images.py`, проверьте `--check`, запустите `--os` → `run 0` и сравните результат. Не редактируйте двоичный `system.img` вручную и не отправляйте учебные изменения в основную ветку без решения владельца. Оригинал всегда доступен через исходный коммит и сохранённую историю.
